# 플랫폼과 성능 기준

확정일: 2026-09-14. 플랫폼·렌더링·입력·네트워크·최적화 작업 전에 읽는다. 사용자 확정 요구와 기술 제안을 구분한다.

## 확정된 제품 요구

| 항목 | 기준 |
|---|---|
| 플랫폼 | PC와 모바일 크로스플레이 |
| 출시 우선순위 | PC·Android 우선, iOS 후속 지원 |
| 성능 | 저사양 기기에서도 60 FPS 목표 |
| 품질 정책 | 저사양에서도 게임 규칙과 조작에 필요한 정보는 유지 |

30 FPS를 저사양의 기본 목표나 완료 조건으로 낮추지 않는다. 60 FPS는 요구 목표이며 현재 달성했다는 뜻이 아니다. PC 운영체제 범위, 최소 Android 기종·OS·RAM·GPU, 후속 iOS 최소 기기는 아직 정하지 않았다. 모든 구형 기기에서 60 FPS를 보장하는 요구로 해석하지 않는다.

## 현재 구현과 목표 사이의 차이

- 현재 프로젝트는 HDRP 17.3.0이다. 공식 플랫폼 표에서 Android·iOS는 HDRP 미지원, URP 지원이다. 현재 설정으로 모바일 대응이 완료된 것으로 보지 않는다. [Unity 6.3 파이프라인 비교](https://docs.unity3d.com/6000.3/Documentation/Manual/render-pipelines-feature-comparison.html)
- 차량 코드는 키보드 입력과 로컬 Rigidbody 주행이다. 터치 조작, 네트워크 동기화, 권한 판정, 매칭·세션은 아직 없다.
- 기존 배치 검사는 참조와 수동 물리 동작을 확인한다. Android 빌드·장시간 발열·60 FPS·PC와의 동시 접속을 확인한 결과가 아니다.

## 우선 준비 작업 — 제안, 미구현

1. **복구 기준과 URP 전환 검증:** 현재 상태를 버전 관리에 기록하고 별도 복사본에서 PC·모바일 공통 URP 구성을 검증한다. HDRP 패키지 제거만으로 전환이 끝났다고 보지 않는다.
2. **렌더 의존성 조사:** GameScene과 빌드 씬, 재질·셰이더·Volume·조명·카메라·효과를 확인한다. VehicleTireEffects의 `Shader.Find("HDRP/Unlit")`도 전환 대상이다. 차량 주행 수치와 .meta GUID는 보존한다.
3. **최소 기기 선정과 실기기 빌드:** Android 최소 기기와 저사양 PC를 지정하고, 같은 시험장·품질 설정·입력 조건으로 빌드와 측정을 반복할 수 있게 한다. PC의 상세 OS 범위와 iOS 기준은 별도로 확정한다.
4. **공통 입력 명령:** 키보드와 터치가 같은 VehicleDriveCommand 의미를 사용하도록 입력원을 분리한다. 조향·가속·제동·핸드브레이크를 동시에 조작할 수 있는 터치 UI와 중단/복귀 처리를 검증한다.
5. **최소 크로스플레이 시험:** PC와 Android 각 1대가 같은 세션에 접속해 이동·충돌·연결 해제를 검증한다. 이 시험은 최대 동시 인원 성능 검증과 구분한다.
6. **네트워크 판정 설계:** 차량 물리·충돌·피해·미션·보상의 판정 주체, 상태 동기화와 보간/예측, 재접속 정책을 정의한다. 서버가 최종 판정하는 구조를 우선 검토하되 SDK·서버 호스팅·동시 인원·틱률은 아직 선택하지 않는다.

PC에만 HDRP를 유지하고 모바일에 별도 렌더 구성을 만드는 방식보다 공통 URP에 품질 단계를 두는 안을 우선 검토한다. 이는 유지보수와 검증 범위를 줄이기 위한 제안이며 아직 프로젝트 설정을 전환하지 않았다. HDRP와 URP 프로젝트 자산은 호환 검토가 필요하다. [HDRP 17.3 호환성](https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@17.3/manual/System-Requirements.html)

## 성능 측정과 품질 조절

- 60 FPS의 프레임 시간 기준은 약 16.67ms다. CPU·GPU 각각의 시간과 프레임 지연 분포를 기록한다. 평균 FPS만으로 통과시키지 않는다.
- 기준 기기·OS·빌드·해상도/렌더 스케일·품질·차량 수·이펙트 수를 측정 기록에 남긴다. 메모리·GC 할당·물리 비용·네트워크 트래픽도 함께 관찰한다.
- 제안 시험은 일정한 코스에서 20~30분 연속 실행하여 발열 이후 프레임 안정성을 확인하는 것이다. 허용 프레임 급락·로딩 예외·메모리 한계는 최소 기기와 게임 규모가 정해진 뒤 수치화한다.
- Development Build에 Profiler를 연결해 병목을 찾고, 최종 성능은 배포 설정에 가까운 빌드에서도 재확인한다. [Unity 대상 플랫폼 프로파일링](https://docs.unity3d.com/6000.3/Documentation/Manual/profiling-target-device.html)
- 우선 조절 후보는 렌더 스케일, 그림자 거리·해상도, 추가 조명, 후처리, LOD, 장식 효과량이다. 기기별 화질 변화가 충돌·피해·그립·게임 판정 차이가 되지 않도록 한다.
- 원격 차량과 AI, 접지 검사, 파티클·자국의 비용은 별도 측정한다. 풀링·물리/AI 갱신 범위 조절은 실제 병목에 맞춰 도입하고 플레이어 차량의 조작 감각을 검증한다.
- 렌더 FPS, 물리 Fixed Timestep, 네트워크 틱률을 서로 같은 설정으로 취급하지 않는다. 현재 Fixed Timestep 0.02s를 60 FPS 목표만을 이유로 자동 변경하지 않는다.

## 다음 결정이 필요한 항목

최소 Android 기기와 저사양 PC 사양, 내부 렌더 해상도 범위, 동시 플레이어·교통 차량 수, 맵 규모, 허용 지연과 통신량, 서버 운영 방식이 미정이다. 결정 전에는 임의의 숫자를 제품 요구로 확정하지 않는다.

이번 단계는 요구와 준비 작업의 문서화다. URP 전환, 모바일 빌드, 터치 UI, 네트워크 구현, 실기기 성능 검증은 아직 수행하지 않았다.
